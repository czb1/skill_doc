# 代码提交审查技能

一种结构化的方法来审查单个 git 提交的代码质量、设计模式、业务逻辑正确性和可操作的改进建议。

## 何时使用

在以下情况下使用此技能：
- 审查特定的 git 提交以检查代码质量
- 检视代码修改是否存在 DFX（可开发性、可测试性、可维护性）、可靠性、性能问题
- 检查提交是否正确使用设计模式
- 评估变更集的代码质量和业务逻辑正确性
- 在提交中查找 bug、反模式或改进机会
- 结合外部资料（接口文档、需求文档等）进行综合审查
- 审查拉取请求或合并请求的变更

## 前置条件

- 能够访问包含该提交的 git 仓库
- Git 命令行工具可用
- 提交的哈希值或引用标识符
- 如有外部参考资料，需用户提供文档内容

## 审查工作流程

### 步骤 1：收集提交信息

首先检查提交的元数据和范围：

```bash
git show <commit-hash> --stat
```

这会显示变更的文件、增行/删行数量，并帮助你理解变更的范围。

同时获取提交消息和作者信息：

```bash
git log -1 <commit-hash> --format="%H%n%an%n%ae%n%ad%n%s%n%b"
```

### 步骤 2：审查完整差异

检查实际的代码变更：

```bash
git show <commit-hash> -p
```

### 步骤 3：多维度代码审查

仔细阅读每个变更的文件，按以下维度进行审查：

#### 3.1 代码基础编码问题
- **命名规范**：变量、方法、类命名是否清晰且符合规范
- **代码格式**：缩进、空格、换行是否一致
- **注释质量**：关键逻辑是否有必要的注释，注释是否准确
- **重复代码**：是否存在复制粘贴的重复逻辑
- **魔法值**：是否有硬编码的数字或字符串应定义为常量

#### 3.2 DFX（可开发性、可测试性、可维护性）
- **函数长度**：方法是否过长（建议不超过 80 行）
- **圈复杂度**：条件分支是否过于复杂
- **耦合度**：类/模块之间的依赖是否合理
- **单一职责**：类/方法是否职责过多
- **接口设计**：接口是否清晰，参数是否合理

#### 3.3 可靠性
- **空指针风险**：是否存在可能的空指针引用
- **异常处理**：异常是否被正确捕获和处理
- **边界条件**：边界条件是否被正确处理
- **资源泄漏**：文件、流、连接是否正确关闭
- **并发安全**：多线程访问是否有合适的同步

#### 3.4 性能
- **不必要的对象创建**：是否在循环中创建对象
- **低效的集合操作**：是否使用了不恰当的集合类型
- **重复计算**：是否存在可以缓存的重复计算
- **不必要的循环**：是否存在可以优化循环逻辑

#### 3.5 业务逻辑审查
- **逻辑正确性**：业务逻辑是否符合预期
- **数据一致性**：数据变更是否一致
- **边界场景**：异常场景是否被处理
- **业务规则**：业务规则实现是否正确

### 步骤 4：结合外部资料审查（如有提供）

当用户提供了外部参考资料时：
1. 解析接口文档、需求文档或其他资料
2. 对比代码实现与文档描述是否一致
3. 检查是否遗漏了文档中要求的场景
4. 验证参数、返回值、错误码等是否与文档匹配

### 步骤 5：评估设计模式使用

评估提交中是否存在设计模式。判断模式属于：
- **显式使用**：提交引入了一个已知模式
- **隐式需要**：代码可以从模式中受益但尚未使用
- **不适用**：变更太简单，不需要应用模式

### 步骤 6：生成审查报告

使用以下模板生成结构化的审查报告：

```markdown

## 基本信息
- **提交ID**：[commit-hash]
- **提交消息**：[commit message]
- **作者**：[author]
- **审查时间**：[timestamp]
- **变更文件数**：[count]
- **变更行数**：[+insertions/-deletions]

## 变更摘要
[简要描述本次提交做了什么]

---

## 一、代码基础编码问题

| 严重程度 | 文件 | 行号 | 问题描述 | 修改建议 |

| 严重程度 | 文件 | 行号 | 问题描述 | 修改建议 |

```

### 步骤 7：输出报告到文件

**重要**：审查完成后，必须将审查报告输出到 Markdown 文件中。

**文件命名规范**：
```
code-review-<commit-hash>-<YYYYMMDD-HHmmss>.md
```
例如：`code-review-a1b2c3d4-20260115-143022.md`

**输出位置**：
- 报告文件必须输出到当前项目的根目录下
- 如果是仓库审查，输出到克隆仓库的根目录
- 如果是本地目录审查，输出到该目录的根目录

**操作方式**：
1. 使用 Write 工具创建报告文件
2. 文件路径格式：`{项目根目录}/code-review-<commit-hash>-<时间戳>.md`
3. 完整写入审查报告的完整内容（不包含代码块标记）

### 步骤 8：提供可操作的建议

当提出改进时，遵循以下指南：

1. **具体明确**：提及具体的文件名、行号和方法名
2. **解释原因**：说明问题的影响和为什么需要修改
3. **提供示例**：给出正确实现的代码示例
4. **考虑范围**：区分立即需要修复的问题和未来改进项

## 常见反模式检查清单

### 代码基础编码
- [ ] 布尔参数蔓延
- [ ] 嵌套数据结构滥用
- [ ] 复制粘贴代码
- [ ] 魔法数字/字符串
- [ ] 长参数列表
- [ ] 上帝方法

### 可靠性
- [ ] 空指针/空集合引用
- [ ] 异常被吞掉或笼统捕获
- [ ] 资源未释放
- [ ] 并发问题

### 性能
- [ ] 循环中创建对象
- [ ] 低效的集合选择
- [ ] 重复计算
- [ ] 不必要的内存分配
