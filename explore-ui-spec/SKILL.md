# UI 组件规格探索 Skill

## 触发场景

当用户需要了解某个 UI 组件或面板的详细设计规格时触发。典型的用户表达包括：
- "探索 XX 面板的规格"
- "给出 XX 的 UI 提示语/文案"
- "需要 XX 面板的具体尺寸参数和颜色"
- "XX 面板的背景色和其他详情是什么"
- "XX 组件的大小、内部按钮元素大小等具体规格"

## 核心原则

1. **从代码中寻找真相**：UI 规格应以代码库中的实际实现为准，而不是猜测或臆断。所有尺寸、颜色、文案值都必须从源代码中确认。
2. **迭代细化**：用户的第一次 prompt 通常只是一个起点。通过多轮追问和补充来逐步完善规格文档，不要试图一次给出所有细节。
3. **结构化输出**：最终呈现应使用清晰的结构化格式（如表格），按面板区域分门别类。
4. **去实体化与通用化**：输出的规格应面向该组件本身，不包含项目特有的绝对路径、域名、IP、密钥等实体信息。

## 执行步骤

### Step 1: 理解用户需求并制定搜索策略

首先理解用户想要探索的是哪个 UI 组件/面板，然后：
1. 确定组件的大致名称（可能是中文、英文或混合）
2. 确定搜索的关键词集合，包括：
   - 组件名称的中文拼音、英文翻译、驼峰命名
   - 相关的功能关键词（如"推荐"、"姿势"、"pose"等）
3. 制定搜索计划：先搜索文件，再搜索内容，最后读取关键文件

### Step 2: 多维度搜索定位组件文件

使用以下搜索策略定位组件相关文件：

**关键词搜索维度：**
- 中文关键词（如组件名称、功能描述）
- 英文关键词（如对应的英文功能名、组件名）
- 拼音关键词（中文的拼音形式）
- 相关缩写或变体

**文件类型定位：**
- UI 组件文件（.ets, .tsx, .jsx, .kt, .swift 等）
- 资源字符串文件（string.json, strings.xml, Localizable.strings 等）
- 样式/主题文件（theme, style, colors 等）
- 配置文件（config, properties 等）

**搜索操作：**
1. 使用 `grep` / 搜索工具按关键词搜索全仓库
2. 使用文件模式匹配（glob）定位相关组件文件
3. 优先阅读主组件文件（View, Header, CardView 等）

### Step 3: 逐层读取和分析关键文件

按以下优先级顺序阅读文件：

#### 3.1 读取主 UI 组件文件
从最核心的组件文件开始：
- 面板主视图（如 `XXXView.ets`）
- 头部组件（如 `XXXHeader.ets`）
- 列表/卡片组件（如 `XXXCardView.ets`）

从中提取：
- 布局参数（宽高尺寸、间距、边距、内边距）
- 圆角半径
- 组件的组织结构

#### 3.2 读取资源字符串文件
定位并读取组件相关的所有 UI 提示文案和翻译：
- 定位资源文件的路径（如 string.json、string.xml）
- 读取组件相关的所有 key-value 对
- 记录完整的 UI 提示语文本
- 按功能分类整理（按钮文案、引导提示、错误提示、声明文案等）

#### 3.3 查找颜色和字体参数
搜索组件文件中的颜色和样式定义：
- 搜索 `backgroundColor`、`BACKGROUND_COLOR`、`background` 等颜色相关关键词
- 搜索 `fontColor`、`FONT_COLOR`、`Color.`、`fontSize` 等字体相关关键词
- 搜索 `TAB_FONT_SIZE`、`CARD_TITLE_FONT_SIZE` 等尺寸常量
- 记录每个 UI 元素的确切颜色值和字号

### Step 4: 按模式/状态分类整理

根据组件的不同模式或状态分类整理规格：
- 正常模式/直板机模式
- 折叠模式/半折叠模式
- 不同屏幕方向（横屏/竖屏）
- 不同 Tab 状态（选中/未选中）
- 不同数据状态（有数据/无数据/加载中/错误）

如果用户指定了某个特定模式，聚焦于该模式的信息。

### Step 5: 结构化呈现结果

按以下格式组织输出：

```
## [组件名称] 规格文档

### 面板整体
| 参数 | 值 | 说明 |
|------|-----|------|
| width | xxx | xxx |
| height | xxx | xxx |
| radius | xxx | xxx |

### 头部区域
| 参数 | 值 | 说明 |
|------|-----|------|
| ... | ... | ... |

### [其他区域]
| 参数 | 值 | 说明 |
|------|-----|------|
| ... | ... | ... |

### 颜色汇总
| 用途 | 颜色值 | 说明 |
|------|--------|------|
| ... | ... | ... |

### UI 提示语汇总
| 资源 Key | 文本 | 说明 |
|---------|------|------|
| ... | ... | ... |
```

### Step 6: 迭代补充

用户可能会要求补充遗漏的信息（如颜色、背景色、字体等）或过滤掉不需要的内容：
1. 仔细理解用户的补充请求
2. 返回 Step 3 进一步搜索相关信息
3. 更新结构化文档，保持信息完整和准确
4. 移除用户明确不需要的模块或信息

## 关键提示

1. **不要假设值**：始终从代码中确认每个值，不要凭空猜测或补充代码中未出现的值。
2. **多轮沟通**：用户通常不会第一次就把所有需求说清楚，通过补充和细化来逐步完善。
3. **保持组织清晰**：使用表格和分类让信息一目了然，便于用户快速查找所需内容。
4. **注意单位**：在 HarmonyOS/ArkUI 中默认单位为 vp（virtual pixel），记录时要注明单位。
5. **颜色记录**：记录颜色时保留原始格式（如 #RRGGBB、rgba、Color.White 等）。

## 输出格式规范

最终输出的规格文档应包含：
- 组件整体尺寸（宽、高、圆角）
- 各子区域的规格（头部、列表、按钮等）
- 颜色参数汇总
- 完整的 UI 提示文案清单
- 状态说明（不同模式的规格差异）

输出时注意去实体化：移除绝对路径、项目名、域名、IP 等敏感信息，只保留组件规格本身。
